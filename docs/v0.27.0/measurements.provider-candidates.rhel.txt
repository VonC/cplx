WHAT IT CORRECTS. The previous scope probe grouped objects by their internal
       DT_SONAME, and reported 95 SONAMEs offered more than once. That is not
       the loader's model. For a DT_NEEDED entry the loader searches each rpath
       directory IN ORDER for a file with that EXACT NAME; a differently named
       object carrying the same internal SONAME is never a candidate unless a
       path or a symlink exposes it under the needed name. The 95 therefore
       counted development aliases such as libBrokenLocale.so beside
       libBrokenLocale.so.1, which are not competing candidates for any lookup.

       Read the loader's way, the number is 20, and the conclusion is unchanged
       but now rests on the right model.

THE COUNTS RULE 1 IS WRITTEN AGAINST:

       54 distinct DT_NEEDED names are required by the shipped objects.
       20 of those names have more than one candidate path in the scope.
       All 20 resolve, through their links, to ONE file.
        0 resolve to different content.

       So the unmodified archive PASSES rule 1. That is the positive control the
       acceptance requires: a rule 1 that over-refused would fail here, on 20
       names, and this run is what shows it does not.

WHY RULE 2 CANNOT BE FOLDED INTO RULE 1. The libbfd pair carries two different
       FILENAMES, so no DT_NEEDED name ever has both as candidates and rule 1 is
       silent on them by construction. Only a declared family list makes them
       refusable, which is why the two rules are separate rather than one rule
       with an exception.
