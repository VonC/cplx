--- reading, added when the output was retained ---

This is the R-rs half of the Step 0 baseline. Seventeen cases, no failures, and
the identity is asserted rather than requested: `R-rs` on the header line is what
the run asked for, and `baseline engine` confirms it by reading rsync's own
file-list banner out of the case log. That banner is printed by the transfer, not
by a decision to transfer, which is the distinction the whole engine assertion
now rests on.

The two root-file cases are the point of this capture. With rsync present, a FIFO
planted at the destination `.env` is replaced by a regular file carrying the
archive content, and a destination `.env` that is a symlink onto a regular file
outside the prefix is likewise replaced while that external target stays
identical in content and mtime. Exit 0 in both. These are the two behaviours
Step 3 changes for the fallback engine only, so without them recorded Step 3
would have nothing to change against. Promptness needs no separate assertion:
every case runs under the twenty-second watchdog, so a blocking engine returns
124 and fails the expected exit, which is what the calibrated watchdog control
shows `cp -a` does to a FIFO.

**What this harness deliberately cannot say.** There is no fallback expectation
here and no fallback marker recognition. An earlier body guessed at Step 1's
wording, and the guess was unsafe in the direction that matters: the plan has
Step 1 emit a selection line before archive discovery while both rsync call sites
stay unchanged, so a run could announce a fallback selection and still die at the
unchanged mirror having copied nothing. Recognising that line would have reported
`engine fallback, read from the run trace` for exactly such a run. Step 0 asserts
only the two states it can witness, rsync operating and nothing operating, and
refuses a target identity outright for any installer able to select a fallback.
Selection becomes a separately named assertion when Step 1 defines its trace, and
proof that the selected engine copied stays with the operation and post-state
cases.

**The controls now include the oracle that reads the setup.** `control
fixture-shape` plants a plain regular file where a case declares an exact
symlink, and requires refusal on the shape rather than on anything downstream. It
runs here rather than only on a developer host because a shared-mode error in
that oracle could accept a false declaration on both targets while every ordinary
case stayed green: the fixture oracle interprets the setup every behavioural
conclusion rests on, so it has to be recalibrated in the evidence being read, not
in an anecdote about a different machine.

`control omitted-root` matters on this host specifically. It plants a newer decoy
archive in the pinned `$HOME/pkgs`, a root `install_pkg.sh` line 393 searches and
the first resolver ignored. This is a real deployment account whose home holds
archives, so under that resolver the installer could have consumed one of them
while the harness approved the declared synthetic archive, returning exit 0 and
satisfying every payload check. Every case runs with `HOME` pinned inside
scratch, and the archive identity prints its searched root rather than a bare
basename, because one name can exist under more than one of the four roots.

`all 28 present` covers every external command the harness runs, including the
child `bash` the case runner looks up on PATH, plus the plan's five
verification-only additions. `diff` is the one command not invoked at step 0: it
is the manifest comparison's tool, and this line is the promised evidence that
step 5's acceptance gate will have it on this target.
