--- reading, added when the output was retained ---

This is the RHEL half of the step 1 evidence, and it is the half that can show
the override doing anything, because it is the only supported target where rsync
exists to be overridden.

**The six selections.** Unset, `0`, `yes`, `true` and empty all select rsync and
print the resolved binary path. Only `1` selects cp, and it says it was forced.
That is the design's fail-safe reading made visible: `yes` and `true` look truthy
and are not treated as such, because the consumers of this variable are wrapper
scripts in another repository rather than people, and a script that sets a
plausible value should get the safe engine rather than the requested one.

**The divergence, recorded rather than described.** `step1 forced still operates
rsync` passes: with the fallback forced, the run selects cp and rsync still
mirrors, because step 1 changes no call site. That assertion is true now and will
be false after step 2, which is the point of it. Step 2 should change its expected
operation and post-state, not quietly delete it, or the transition it exists to
mark disappears with it.

**Two ordering controls, calibrating different things.** `selection-no-discovery`
feeds the oracle a well-formed selection line with no archive discovery marker,
and it must refuse on the missing marker rather than report an ordering it could
not have established. `selection-out-of-order` feeds exactly one marker followed
by one otherwise-valid selection line, and it must refuse on the comparison. The
second exists because the first proves the wrong half: an earlier version had
only it, and the branch implementing Q06, the guarantee this whole step adds, had
never executed. The six positive cases below cannot supply it, since a correctly
ordered trace only exercises the passing path and no installer emits a wrongly
ordered one.

**What the identity line deliberately does not say.** It is not `R-rs` and not
`R-fb`. Those are acceptance matrix cells describing one engine, and this run
holds six selections and two operations. Calling it a cell would have made a
selection suite look like engine acceptance, which is the same conflation the
step 0 review spent two rounds removing from the engine assertion.

**The step 0 suite rides along.** The dispatch is cumulative, so the seven
controls and the whole step 0 baseline ran against the candidate here, at exit 0
with the canary symlink surviving and both root-file shapes behaving as they did
for the published installer. That is the "no behaviour change" claim tested
rather than asserted: the candidate installs exactly as the pre-change installer
did on this target.

**Fingerprints.** The installer is `312be8ae`, 535 lines, `fallback: yes`, which
is this branch's candidate and not the deployed `3c1f6a56`. The harness whole-file
digest `cb2915f5` pins this capture to the committed cplx source; the shared-body
digest `65451888` is the value the Debian capture also reports, from the
consuming project's copy, which is what shows the two ran the same code.
