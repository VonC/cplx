WHY THIS CAPTURE IS AUTHORITATIVE AND NOT MERELY PRESENT. The verdict below
         carries FOUR digests, and all four are asserted by a host reading this
         file through `--capture`: `harness` names the instrument, and
         `wrapper-sha`, `setenv-sha` and `retained-sha` name the three files it
         measured. A capture bound only to its instrument would certify a run
         over inputs nobody compared to the ones present, which code review
         round 2 of step 0 demonstrated with an unchanged-vocabulary broken
         wrapper.

Host note: step 1 is host-agnostic ACROSS POSIX HOSTS by plan decision P1, and
         this run is on RHEL only because RHEL is the nearest POSIX host. The
         authoring and reviewing host is Windows, which cannot create the
         fixture's symlinks; the harness measures that with a probe and reads
         this capture instead.

THE FLIP THIS STEP EXISTS TO PRODUCE, against the step 0 baseline:

  step 0:  helpers-seeing-search-path  7 of 7,  interpreter sees it
  step 1:  helpers-seeing-search-path  0 of 7,  interpreter still sees it
  step 1 venv path:      helpers-seeing-search-path  0 of 13, second arm too
  step 1 second call:    helpers-seeing-search-path  0 of 9

         Both halves are asserted. A change that took the helper count to zero
         by also starving the interpreter would satisfy a helpers-only count and
         break the wrapper, so `interpreter-still-sees-it` and
         `interpreter-value-is-the-shipped-path` are separate cases.

         THE SEVEN CALLS ARE ASSERTED PRESENT BEFORE THE COUNT IS READ. The
         first run of this suite reported `helpers-seeing-search-path 0` while
         measuring NOTHING: the suite had not planted its shims, so PATH
         resolved every helper to the real tool and no call was logged. The
         presence assertions failed and caught it. Without them this step would
         have reported the scope rule satisfied on an empty log, which is the
         exact failure mode this requirement exists to remove.

W3, the empty saved value: exercised with a VARIANT fixture whose planted setenv
         exports an empty value, since the shipped setenv always exports a
         non-empty one. The interpreter records `empty` rather than `unset`, and
         the shipped setenv's own bytes are asserted unchanged at the digest
         step 0 recorded.

ALL FOURTEEN POST-SOURCE SITES ARE MEASURED, not the seven a `--version` call
         reaches. The `-m venv` variant runs the post-interpreter branch, where
         `cp`, `grep` and both `sed` sites live and nowhere else, and it runs the
         VIRTUAL_ENV arm of the interpreter `if`, so the SECOND restore site is
         measured from a run rather than counted in the source. A third run over
         the already-surgered tree reaches the `else` arm of the relink `if`,
         the fourteenth site, which no first call can execute.

         The venv run makes THIRTEEN post-source helper calls and none sees the
         search path; the second call makes NINE and none sees it either. Every
         helper name is asserted PRESENT case by case before any zero is read,
         so a branch that stopped executing fails rather than passes.

         The second call's nine are two more than the seven a repeat would
         suggest, and the reason is this fixture rather than the wrapper:
         `${DIR}/pip` links to `current/bin/pip3`, which the fixture never
         plants, so the `-e` test is false on every call and both pip links are
         made again. A deployment has pip3 and takes that branch once.
