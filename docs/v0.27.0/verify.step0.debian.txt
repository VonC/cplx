This is the Debian half of the Step 0 baseline, and it is still the half that
matters most: this agent is where Q19 actually bites, and the run records the
failure exactly as the requirement describes it. Exit 5 in the mirror phase, no
populated tools tree, and the staging directory left behind, which is the
recovery contract the design states rather than assumes. The last two are
asserted by the `not-deployed` oracle inside the case runner, so the case cannot
pass on status alone.

**What this run is not called, and why.** Build 36 labelled itself `D-fb` and
then claimed that label was asserted by `engine none`. Code review refuted both
halves. D-fb is the cell where the fallback engine is selected and runs; this
installer has none and dies at the mirror, so no engine ran at all. And absence
of rsync's banner proves only that rsync did not run, which is equally true of a
successful fallback, so it can never be affirmative evidence for one. The
identity here is `Debian/no-rsync/no-engine`, not a matrix cell but the
pre-change state expected to become one, and the header says so. The engine
assertion matches: `no engine ran` requires no trace **and** a failed run, so the
claim is that nothing copied rather than that rsync did not.

**And what the harness no longer even tries to say.** A later body recognised a
guessed `copy engine: fallback` marker so that a future run could claim D-fb.
That was withdrawn as unsafe in the direction that matters. The plan has Step 1
emit a selection line before archive discovery while both rsync call sites stay
unchanged, so on this agent that line could say fallback and the same run still
die at the unchanged mirror having copied nothing, and the harness would have
reported `engine fallback, read from the run trace`. A guessed phrase would have
become stronger evidence than the event it describes, on the one target where the
defect actually lives. Step 0 now witnesses two states only, and refuses a target
identity outright for any installer able to select a fallback.

The stage runs in its own shell so the pipeline's rsync shim is not on PATH, and
`rsync : no` records that. If the shim ever leaked onto PATH, the harness would
refuse any target identity and fail preflight rather than record a shimmed
success as Debian evidence.

`control fixture-shape` is new here. It plants a plain regular file where a case
declares an exact symlink and requires refusal on the shape, which recalibrates
on this target the oracle that interprets every fixture. Without it, a
shared-mode error in that oracle could accept a false declaration on both targets
while every ordinary case stayed green.

The root-file FIFO and symlink shapes have no baseline on this target, and that
is a property of the target rather than a gap. Without rsync the installer dies
at the mirror phase and never reaches the root-file loop, so there is nothing to
observe. Their baseline is the RHEL capture's, where rsync is present.

`all 28 present` covers every external command the harness runs, including the
child `bash` the case runner looks up on PATH, plus the plan's five
verification-only additions. `diff` is the one not invoked at step 0: it is the
manifest comparison's tool, and this line is the promised evidence that step 5's
acceptance gate will have it on this agent.
