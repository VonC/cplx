Target: RHEL 9.8, the live deployment install of the published archive
Captured: 2026-09-03, by hand over ssh

WHY THIS WAS TAKEN. Round 2 of the issue asserted one resolution scope per tool
       root, and classified two measured shapes from that assumption. Round 2 of
       the review read the installer instead: `build_elf_rpath` accumulates
       EVERY tool root into one ordered list, dedupes it, and the relocation
       pass applies that single value to every ELF. The directories it adds are
       root/usr/lib64, root/usr/lib, root/lib64, root/lib per tool root plus
       each version directory's lib and lib64. It never adds root/usr/bin.

       Both classifications the issue drew were therefore wrong, and wrong the
       same way: they read directory layout instead of the search list. This
       probe reads the search list.

WHAT IT OVERTURNS, precisely:

  - "libcrypto.so.3 once per tool root is not a collision, different scopes"
    was wrong about the reason. There is ONE scope and both copies are in it.
    It is not a fault because it is the SAME FILE, which is a different rule.
  - "libssl.so.3 twice per tool root is a collision" was wrong outright. One of
    the two copies is under root/usr/bin, which is not a provider directory in
    the scope at all.

WHAT IT ESTABLISHES FOR THE RULE. 95 SONAMEs are offered more than once in the
       one scope, and every one of the 95 is the same file reachable from
       several directories. A refusal rule keyed on "same SONAME twice" would
       refuse this archive 95 times over, all of them false. The rule has to be
       two DIFFERENT files, compared by content digest, offering one SONAME.

       The genuinely different case is cross-SONAME: libbfd-2.35.2-63.el9.so and
       libbfd-2.35.2-66.el9.so sit in the same scope under two SONAMEs. ELF
       carries no universal logical-family identifier, so nothing in the file
       says those two are one family. That relationship must be declared.
