# CPLX closure fixture corpus, v0.27.0
#
# The committed TEXT from which `verify.closure-check.sh` generates the ELF
# objects and the tree shapes its cases need, into its own scratch directory.
# Nothing binary enters this repository, and nothing here is executed: a row is
# a specification, and the harness is what turns it into a file.
#
# WHY THE OBJECTS ARE MUTATED DONORS (plan decision Q07). An ELF with a real
# dynamic section cannot be conjured from text, and the three alternatives were
# each refused with a reason: hand-built hex nobody will review, a compiler as a
# harness prerequisite on both hosts, and committed binary fixtures, which the
# two earlier items of this collection already refused. So the harness FINDS a
# donor on the host it runs on, VALIDATES its ELF class and section shape against
# the `donor` rows below, copies it, applies the row's mutation, and ASSERTS the
# mutated semantic result before any case is allowed to use it. A donor that
# fails validation, or a mutation whose asserted result is not observed, is a
# harness failure and never a smaller run.
#
# THE COUNT ROW IS THE POINT OF THE FILE BEING PARSED AT ALL. A corpus that lost
# its tail would otherwise produce a shorter, greener run: fewer fixtures, fewer
# cases, and a verdict that reads exactly like a complete one. The harness reads
# `count`, counts the `spec` rows, and refuses on the difference, so a truncated
# corpus is a failure rather than a smaller run.
#
# Row types, each with its own fixed arity, all columns required:
#
#   count|<n>
#     the number of `spec` rows this file declares.
#
#   donor|<selector>|<elf-type>|<required-parts>|<why>
#     what the harness must find on the host before it may build the objects of
#     that selector. `required-parts` is a comma separated list of the program
#     header or dynamic entries the donor has to carry.
#
#   spec|<id>|<kind>|<donor>|<placement>|<mutation>|<assert>
#     id           the name a case cites, unique across the file
#     kind         object, an ELF derived from a donor; tree, a directory or a
#                  plain file shape with no ELF content
#     donor        the donor selector, or `-` for a tree
#     placement    the path, relative to the prepared prefix, the fixture is
#                  generated at
#     mutation     the transformation applied to the donor, or the shape planted
#                  for a tree, as `<verb>` or `<verb>:<operand>`
#     assert       the semantic result the harness must OBSERVE on the generated
#                  fixture before any case may use it. This column is why a
#                  mutation that silently did nothing cannot be mistaken for one
#                  that worked.
#
# HOW A MUTATION REACHES A REAL DYNAMIC SECTION, added by Step 3 when the engine
# behind these rows was written. Nothing here rebuilds an ELF: the donor's own
# `.dynstr` carries the names and its own `.dynamic` carries the entries, and a
# mutation only moves what is already there.
#
#   the name slots      the LAST 256 BYTES of the donor's `.dynstr`, taken as four
#                       64-byte slots. A mutation writes its name into a slot and
#                       repoints a dynamic entry at that offset, so no fixture
#                       name is limited by the length of the string it replaces.
#                       The bytes it overwrites are symbol names, which nothing in
#                       this effort reads: the checker reads dynamic entries and
#                       version records, and both keep their own strings.
#   the spare slot      the linker pads `.dynamic` past its terminating DT_NULL.
#                       `needed-add` turns the FIRST DT_NULL into a real DT_NEEDED
#                       entry and leaves the next spare slot as the terminator, so
#                       the need is ADDED rather than substituted for another.
#
# Both shapes are donor requirements rather than assumptions, which is why the
# `shared` row names them: a donor that cannot supply either is refused before a
# fixture is generated from it, and the harness reports UNANSWERED rather than
# building an object whose mutation could not take.
#
# The names inside the fixtures are deliberately `cplx`-prefixed inventions
# rather than real library names, except where a case is about a real one:
# `libssl.so.3` appears because the design's subject rule turns on a second copy
# of it under `root/usr/bin`, and the `libcplxbfd` pair stands in for the
# measured `libbfd-2.35.2-63` and `-66` generations without pinning a version
# this corpus would then have to track.
#
# Steps 3 and 4 extend this file as their cases need. A row is added here and
# reviewed before the case that consumes it exists, which is the same order the
# host-tool contract follows. STEP 3 ADDED THREE AT SUBMISSION, and each exists
# because a case would otherwise have proved something narrower than it claims:
#
#   provider-donor-need     one text provider per DT_NEEDED name the validated
#                           donors carry, planted into a provider directory. A
#                           donor keeps its own needs, so without this row every
#                           generated subject would refuse on the donor's `libc`
#                           and the planted defect would be one refusal among
#                           several rather than the only one.
#   provider-first-libssl   the FIRST `libssl.so.3`, in a provider directory. The
#                           subject rule is about a SECOND copy, and with no first
#                           copy the index would hold no such name at all, which
#                           satisfies "absent from the index" for the wrong reason.
#   subject-need-provider   a real object at the name `subject-site-packages-need`
#                           depends on. It is the ONE subject in the step 3 tree a
#                           DT_NEEDED edge reaches, so the unreferenced finding has
#                           a negative control instead of naming every subject.
#
#
# ROUND 1 OF THE STEP 3 CODE REVIEW ADDED TWO MORE, and both exist because a
# reproduced false-green path had no fixture:
#
#   reader-needed-value-unreadable   a DT_NEEDED entry whose string offset falls
#                                    outside the string table. A supported reader
#                                    exits 0 and prints the raw value with NO
#                                    brackets, so a parser matching only the
#                                    bracketed shape drops the entry and the
#                                    object resolves nothing and refuses nothing.
#                                    `needed-offset-corrupt` is the verb, and it
#                                    repoints the first DT_NEEDED value rather
#                                    than touching the string table.
#   subject-libssl-consumer          an object that NAMES `libssl.so.3`, without
#                                    which the second copy under `root/usr/bin`
#                                    is unreferenced for want of any consumer at
#                                    all, and a reachability map keyed by name
#                                    rather than by resolved path passes.
#
# ROUND 2 ADDED THREE, for the ordinary shape the round 1 repair still got wrong:
# a soname symlink and its differently named target, `libz.so.1 -> libz.so.1.2.11`
# in the wild. `provider-alias-target` is the real file, `provider-alias-link` is
# the soname beside it, and `subject-alias-consumer` names the soname. Without
# the three, a reachability rule that resolves an alias by NAME rather than by
# file identity reports a normally loaded library as unreferenced, and no case
# says so.
#
# ROUND 4 ADDED FOUR, for the shape a whole-path lookup cannot resolve: a
# SYMLINKED DIRECTORY. `tools/python/current -> version` is the alias layout this
# effort already reads, and the observed scope then holds `current/lib` while the
# walk, which does not follow a symlinked directory, records the object under
# `version/lib`. `dir-alias-target` is the real file, `dir-alias-soname` the
# soname beside it, `dir-alias-directory` the directory link, and
# `dir-alias-consumer` the object that names the soname. All four are needed
# together: the directory link has to be applied before the name inside it means
# anything, and without the consumer no edge selects the path at all.
#
# ROUND 5 ADDED THREE, all of them link chains a resolver must follow the way the
# kernel does. Each row builds its whole shape, and each asserts with `-ef` that
# the HOST reaches the same file, so the fixture states the right answer rather
# than the harness assuming it:
#
#   chain-relative-parent   a link whose target climbs out of its own directory
#                           and comes back down through an alias directory,
#                           `../../version/lib/x` under `current -> version`. The
#                           components INSIDE a target have to be resolved too.
#   chain-through-updir     a target that goes up through a link directory,
#                           `../linkdir/../lib/x`. `..` applies to the directory
#                           the resolution actually reached, so reducing it
#                           before the link is expanded lands somewhere else.
#   chain-nine-links        nine valid links ending at one real library, which a
#                           supported host resolves. A bound tighter than the
#                           kernel's would refuse a tree that works.
#
# ROUND 3 ADDED ONE, and it is a COST fixture rather than a semantic one.
# `alias-scaling-population` replicates the alias shape above at a size the
# harness chooses, so the cost of resolving aliases can be MEASURED at two
# populations instead of argued about. A rule that compares file identities pair
# by pair grows with the product of the links and the subjects; one that reads
# where each link points grows with the population. Only a run at two sizes tells
# them apart, and nothing in this schema caps the number of aliased libraries.
#
# A row whose placement repeats another row's is not a conflict: each step's suite
# prepares its OWN tree from the rows its cases cite, so two steps may generate
# different objects at one path without ever meeting.
#
