WHAT IT SPLITS, and why only one half needed a deployment. The question "is the
       shipped libssl coherent with the shipped libcrypto" has two halves. Does
       the shipped provider DEFINE what the shipped consumer NEEDS is a property
       of the two files: an rpath changes which file is selected, never what a
       file defines, so no relocation and no run is required to read it. Does
       the consumer SELECT the shipped provider is the rpath question, and
       relocation-force-rpath settled that by giving every shipped library an
       rpath of its own.

       This capture answers the first half conclusively and says so; it does not
       claim the second.

THE COMPARATOR CARRIES ITS OWN CONTROL, and it earned it. The first run of this
       probe reported all six needed nodes missing while the inventory printed
       directly above it showed every one of them defined. The membership test
       compared a space-delimited pattern against newline-delimited data, so it
       could only ever answer "missing". The verdict below is believed only
       because the two control lines show the comparator answering both ways.

TWO THINGS THIS MEASURED THAT THE REQUIREMENT NEEDED. First, the eight
       OPENSSL_3.x lines the earlier probe reported as missing nodes are an
       isolation artifact: every node is defined. Second, libssl.so.3 ships
       TWICE per tool root, in root/usr/bin and root/usr/lib64, and the two are
       NOT identical copies: their version-need sets differ. Same SONAME, same
       ABI major, different builds.
