--- reading, added when the output was retained ---

Cases 1 and 2 answer the question the round 4 plan review raised, and they
disprove the writer's claim rather than confirming it. Through the exact fresh
forms this design specifies, `rsync -av --delete src/ dst/`, the fallback's
empty-then-`cp -a src/. dst/`, `rsync -av file prefix/` and
`cp -a --remove-destination src prefix/name`, both engines reproduce the source
mtime to the nanosecond. rsync 3.2.5 synchronizes fractional mtimes. The claim
that `rsync -a` transfers whole seconds only is withdrawn: it was never
measured and it is wrong.

Case 3 is the behaviour that actually exists, and it is a different thing.
Against a destination file already present with the same size and the same
integer second but a different fraction, rsync's default quick check decides no
transfer is needed and the destination keeps its own mtime. That is a skip
decision on a populated destination, not truncation during transfer. The
fallback cannot reach that state at all, because it empties the destination
before copying.

Scope, so the result is not over-read:

- The equivalence comparison installs into two fresh prefixes. No destination
  file pre-exists, so no quick check runs, and cases 1 and 2 are what govern it.
  The manifest keeps full mtime precision.
- On a real redeployment over a populated prefix the two engines are therefore
  not interchangeable for entries that survive: rsync may skip what the fallback
  always rewrites. This is standard, documented and unchanged rsync behaviour on
  the path this effort deliberately leaves alone, not a defect introduced here.
  It is recorded because "the two engines produce the same tree" is only true of
  the fresh case that the equivalence run actually measures.
